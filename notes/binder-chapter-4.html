上一章已经用 service 命令走通了一次 IServiceManager.checkService。这一章继续用系统服务，不再写 App：App 层的 AIDL 只是系统 AIDL 的一个子集，真正复杂的地方在系统服务里——大量进程、生命周期、回调、死亡通知和跨语言对象。

样本选 servicemanager。它同时用到本章要讲的五种能力：

  • Parcelable：ServiceDebugInfo 数组；
  • in / out / inout：framework 里的 IActivityManager、IPackageManager 接口；
  • oneway：IServiceCallback 和 logFgsApiBegin；
  • callback：registerForNotifications；
  • DeathRecipient：servicemanager 自己就继承 IBinder::DeathRecipient。

先把结论放在前面：这些能力不是“App 层 API”，而是系统服务维持对象图、处理进程死亡的基础设施。读完后你应该能回答：为什么 servicemanager 能自动删掉死掉的服务？为什么 callback 接口必须是 oneway？为什么 service call 不能用来验证 oneway？

系统 AIDL 和 App AIDL 的生成代码一样，但约束更多：HAL 和 vendor 服务通常要求 stable AIDL / VINTF 声明，接口一旦冻结就不能随意改字段；跨 system / vendor 分区时，Parcelable 的类版本、SELinux 和 binder context 都会参与校验。这也是本章坚持读 AOSP 源码的原因：这些约束在 App 层看不到。

一、Parcelable：ServiceDebugInfo 数组

先看一个能直接在真机上验证的 Parcelable 接口。IServiceManager 里有一个只读方法：

ServiceDebugInfo[] getServiceDebugInfo();

对应的 Parcelable 只有两个字段：

parcelable ServiceDebugInfo {
    @utf8InCpp String name;
    int debugPid;
}

name 是服务名，debugPid 是注册时记录的 PID。@utf8InCpp 只影响 C++ 后端的字符串表示，不会改变 Java 的字段顺序。生成代码在服务端写入时用 writeTypedArray：

case TRANSACTION_getServiceDebugInfo:
{
    android.os.ServiceDebugInfo[] _result = this.getServiceDebugInfo();
    reply.writeNoException();
    reply.writeTypedArray(_result, android.os.Parcelable.PARCELABLE_WRITE_RETURN_VALUE);
    break;
}

服务端实现也不复杂，就是把注册表里的名字和调试 PID 抄出来：

Status ServiceManager::getServiceDebugInfo(std::vector<ServiceDebugInfo>* outReturn) {
    if (!mAccess->canList(mAccess->getCallingContext())) {
        return Status::fromExceptionCode(Status::EX_SECURITY, "SELinux denied.");
    }

    outReturn->reserve(mNameToService.size());
    for (auto const& [name, service] : mNameToService) {
        ServiceDebugInfo info;
        info.name = name;
        info.debugPid = service.ctx.debugPid;
        outReturn->push_back(std::move(info));
    }

    return Status::ok();
}

真机上直接调用它。事务码 14 对应 getServiceDebugInfo：

0x00000010: 0000000c 006f0044 006b0063 0062004f '....D.o.c.k.O.b.'
...

service 只打印 Parcel 的十六进制，不做类型解码。按 ServiceDebugInfo { name, debugPid } 的字段顺序解析后，部分条目如下（抓取时刻）：

这张表说明两件事：第一，Parcelable 在系统层就是普通的“字段按顺序写进 Parcel”；第二，debugPid 只是注册时快照，服务进程可能已经重启，不能拿它当实时 PID。

再看一眼原始 Parcel：000000f1 是数组长度，后面的 0000000c 是 DockObserver 的 UTF-16 长度，再往后是字符串内容和 debugPid。Parcel 是紧凑的二进制格式，没有字段名，也没有自描述类型；解析方必须知道 ServiceDebugInfo 的字段顺序，才能把这段字节还原成对象。

生成代码里的 PARCELABLE_WRITE_RETURN_VALUE 是一个返回标记，用于告诉 Parcel 这个对象是“从服务端返回的”，某些实现可以据此复用对象或跳过重复分配。它不改变字段顺序，也不是序列化协议的一部分；真正稳定的契约仍然是 AIDL 和类定义。

debugPid 来自 ServiceManager.cpp 里的 service.ctx.debugPid，这个值在 addService 时从调用方进程上下文里记录下来。服务后来重启、fork 或换进程，注册表里的旧 PID 不会自动更新；因此它只适合调试和归属判断，不适合做实时进程查询。

系统层还会把 Parcelable 和 stable AIDL 绑在一起：HAL 接口通常带 @VintfStability，字段顺序和类型被视为 ABI。给已发布接口加字段、改顺序或换类型，可能让旧 vendor 镜像和新 framework 之间读错位。App 层可以靠同一次编译保证两端一致，系统层不行，必须靠版本和兼容性规则。

!
系统层注意：Parcelable 的字段顺序就是协议。客户端和服务端必须使用同一份 AIDL / 同一个类版本；字段增删、顺序变化或 classloader 不一致，都会让 Parcel 读错位。

二、in / out / inout：系统接口的方向标签

系统 AIDL 经常需要“服务端填充结果再返回”。这时不能只靠返回值，因为一个方法可能有多个输出。framework 里的真实例子：

void getMemoryInfo(out ActivityManager.MemoryInfo outInfo);
void getMyMemoryState(out ActivityManager.RunningAppProcessInfo outInfo);
void querySyncProviders(inout List<String> outNames,
        inout List<ProviderInfo> outInfo);

int getPreferredActivities(out List<IntentFilter> outFilters,
        out List<ComponentName> outActivities, String packageName);

ComponentName getHomeActivities(out List<ResolveInfo> outHomeCandidates);

方向标签的语义可以按“谁写、谁读”来记：

标签客户端写入服务端写入客户端读取
in是否否
out不写是是
inout是是是

生成的 Proxy 会在 transact 之后从 reply 读回 out / inout 参数；Stub 则在调用真实方法后把结果写进 reply。这就是为什么方向标签只能用在 Parcelable、List、Map、数组等引用类型上；int、boolean 这类基本类型默认就是 in，不能声明成 out。

framework 里的调用方通常只是把对象传下去。例如 ActivityManager 的公共 API：

public void getMemoryInfo(MemoryInfo outInfo) {
    try {
        getService().getMemoryInfo(outInfo);
    } catch (RemoteException e) {
        throw e.rethrowFromSystemServer();
    }
}

static public void getMyMemoryState(RunningAppProcessInfo outState) {
    try {
        getService().getMyMemoryState(outState);
    } catch (RemoteException e) {
        throw e.rethrowFromSystemServer();
    }
}

这里的 outInfo / outState 是调用方先 new 好的对象；服务端填充后，Proxy 会从 reply 里把字段读回同一个对象。生成代码大致长这样（用 aidl 35 生成的最小 out Parcelable 示例）：

// Proxy
boolean _status = mRemote.transact(Stub.TRANSACTION_getFoo, _data, _reply, 0);
_reply.readException();
if (0 != _reply.readInt()) {
    f.readFromParcel(_reply);
}

// Stub
Foo _arg0 = new Foo();
this.getFoo(_arg0);
reply.writeNoException();
_Parcel.writeTypedObject(reply, _arg0, android.os.Parcelable.PARCELABLE_WRITE_RETURN_VALUE);

out 和 inout 的区别在 _data：out 不把旧值写给服务端，服务端创建/填充新对象；inout 会先把调用方的对象写进 _data，服务端读取、修改，再写回 _reply。所以 inout 的 Parcel 体积和序列化成本都比 out 高，能用返回值或 out 时不要滥用 inout。

系统接口还要考虑 Binder 事务缓冲区。一次事务的 Parcel 有大小上限，直接返回巨大的 List 容易触发 TransactionTooLargeException。framework 里常见的做法是分页（ParceledListSlice）、回调分块，或者让服务端持有数据、客户端只拿 token。读 IPackageManager 时会看到 ParceledListSlice，就是为解决这个问题。

这一节是源码走读：service call 只能写简单参数，无法安全构造这些 out 对象和 List，所以没有对应的真机命令。读源码时重点看生成的 Proxy / Stub 如何把结果写进 reply、客户端如何读回，而不是背标签。

三、oneway：系统服务里的 fire-and-forget

oneway 表示调用方不等结果。servicemanager 的 callback 接口就是一个真实例子：

oneway interface IServiceCallback {
    void onRegistration(@utf8InCpp String name, IBinder binder);
}

IActivityManager 里也有多个 oneway 方法，例如：

oneway void logFgsApiBegin(int apiType, int appUid, int appPid);
oneway void logFgsApiEnd(int apiType, int appUid, int appPid);
oneway void logFgsApiStateChanged(int apiType, int state, int appUid, int appPid);

用 aidl 35 生成 IServiceCallback.java，可以看到 Proxy 的 transact 多了一个 flag，并且 reply 直接传 null：

@Override public void onRegistration(java.lang.String name, android.os.IBinder binder)
        throws android.os.RemoteException {
    android.os.Parcel _data = android.os.Parcel.obtain();
    try {
        _data.writeInterfaceToken(DESCRIPTOR);
        _data.writeString(name);
        _data.writeStrongBinder(binder);
        boolean _status = mRemote.transact(Stub.TRANSACTION_onRegistration, _data, null,
                android.os.IBinder.FLAG_ONEWAY);
    } finally {
        _data.recycle();
    }
}

生成的 Proxy 会在 transact 时带上 IBinder.FLAG_ONEWAY，客户端把事务写进驱动后立即返回，不等待 BR_REPLY。服务端仍然要读到 BR_TRANSACTION 并执行，但调用方已经走了。因此：

  • oneway 没有返回值，也不能抛回 RemoteException；
  • oneway 调用可能被丢弃或延迟，不能拿它做严格顺序保证；
  • callback 接口通常声明成 oneway，避免服务端在回调客户端时被客户端阻塞。

oneway 也不是“免费异步队列”。它没有 reply，调用方无法知道服务端是否处理成功；高频 oneway 还可能把服务端的 Binder 线程和缓冲区打满（oneway spam）。系统服务里用 oneway 的场景通常有明确边界：日志、状态通知、回调，或者调用方明确不需要结果。

!
别用 service call 验证 oneway。service 命令的 transact(code, data, &reply) 没有设置 FLAG_ONEWAY，它仍然是一次同步事务；即使目标方法声明了 oneway，service call 也不是真正意义上的 oneway 调用。要验证 oneway，必须自己构造带 flag 的客户端，或者读生成的 Proxy 代码。

四、callback：servicemanager 的注册通知

IServiceManager 允许客户端注册“某个服务出现时通知我”：

void registerForNotifications(@utf8InCpp String name, IServiceCallback callback);
void unregisterForNotifications(@utf8InCpp String name, IServiceCallback callback);

servicemanager 的实现里先对 callback 的 binder 注册死亡通知，再把它存进表：

Status ServiceManager::registerForNotifications(
        const std::string& name, const sp<IServiceCallback>& callback) {
    auto ctx = mAccess->getCallingContext();

    if (!mAccess->canFind(ctx, name)) {
        return Status::fromExceptionCode(Status::EX_SECURITY, "SELinux");
    }
    // ... 省略非法服务名、isolated uid、空 callback 检查

    if (OK !=
        IInterface::asBinder(callback)->linkToDeath(
                sp<ServiceManager>::fromExisting(this))) {
        ALOGE("%s Could not linkToDeath when adding %s",
              ctx.toDebugString().c_str(), name.c_str());
        return Status::fromExceptionCode(Status::EX_ILLEGAL_STATE, "Couldn't link to death.");
    }

    mNameToRegistrationCallback[name].push_back(callback);
    return Status::ok();
}

当服务注册时，addService 会遍历这个表，调用每个 callback 的 onRegistration：

if (auto it = mNameToRegistrationCallback.find(name);
        it != mNameToRegistrationCallback.end()) {
    // ... 先确保 lazy service 的 client 状态
    for (const sp<IServiceCallback>& cb : it->second) {
        // permission checked in registerForNotifications
        cb->onRegistration(name, binder);
    }
}

注意 registerForNotifications 的尾部：如果这个服务当前已经注册，它会立刻回调一次 onRegistration；如果服务还没出现，callback 就先留在 mNameToRegistrationCallback 里，等 addService 时再触发。这样客户端不用轮询 checkService，也不需要自己处理“注册早于服务”的竞态。

一个服务名可以挂多个 callback，servicemanager 用 std::vector<sp<IServiceCallback>> 保存；callback 本身必须是一个 Binder 对象（通常是客户端进程里的 IServiceCallback.Stub 子类），否则没有可链接的 binder，也无法在客户端死亡时清理。

这里有三个系统层要点：

  • IServiceCallback 是 oneway，servicemanager 调用 onRegistration 时不会等回调客户端处理完；
  • callback 的 binder 必须保持存活；客户端进程退出后，servicemanager 通过死亡通知把它从表里删掉；
  • registerForNotifications 受 SELinux 的 canFind 限制，不是任何进程都能监听任意服务。

Java framework 里还有一层常用封装：RemoteCallbackList。它帮服务端保存一组 IInterface callback，内部用 linkToDeath / unlinkToDeath 自动清理死亡客户端，并在遍历时处理并发注册/注销。AMS、WMS、PackageManagerService 里大量使用它；读 framework 源码时，看到 callback 列表就要想到死亡通知和并发遍历。

五、DeathRecipient：servicemanager 如何清理死掉的服务

servicemanager 自己就是一个死亡通知接收者：

class ServiceManager : public os::BnServiceManager, public IBinder::DeathRecipient {
public:
    // ...
    void binderDied(const wp<IBinder>& who) override;
};

注册服务时，它对服务 binder 调用 linkToDeath：

// implicitly unlinked when the binder is removed
if (binder->remoteBinder() != nullptr &&
    binder->linkToDeath(sp<ServiceManager>::fromExisting(this)) != OK) {
    ALOGE("%s Could not linkToDeath when adding %s",
          ctx.toDebugString().c_str(), name.c_str());
    return Status::fromExceptionCode(Status::EX_ILLEGAL_STATE, "Couldn't linkToDeath.");
}

服务进程死亡后，驱动发送死亡通知，servicemanager 的 binderDied 会把对应服务、注册回调和 client 回调全部清掉（节选）：

void ServiceManager::binderDied(const wp<IBinder>& who) {
    for (auto it = mNameToService.begin(); it != mNameToService.end();) {
        if (who == it->second.binder) {
            it = mNameToService.erase(it);
        } else {
            ++it;
        }
    }

    for (auto it = mNameToRegistrationCallback.begin();
            it != mNameToRegistrationCallback.end();) {
        removeRegistrationCallback(who, &it, nullptr /*found*/);
    }

    for (auto it = mNameToClientCallback.begin(); it != mNameToClientCallback.end();) {
        removeClientCallback(who, &it);
    }
}

这就是为什么服务进程崩溃后，客户端再次 checkService 会得到 null。注册表不是靠定时扫描清理的，而是由 Binder 的死亡通知驱动。

死亡通知是异步的：服务进程死亡后，Binder 驱动把 BR_DEAD_BINDER 发给所有在对应 node 上注册过死亡通知的进程；接收者通常在 Binder 线程里执行 binderDied，而不是在原来的调用线程里。所以 binderDied 里不能假设持有任何业务锁，servicemanager 的实现也是先遍历自己的表，再逐个清理。

linkToDeath 也不是“绑定生命周期”的自动引用计数：它只负责在 binder 死亡时通知你，真正的引用释放仍然由 sp<> / wp<> 和 Binder 驱动维护。正常注销 callback 时还要 unlinkToDeath，否则 ServiceManager 会一直持有死亡通知接收者；servicemanager 的 unregisterForNotifications 和 removeRegistrationCallback 就是在做这件事。

在 native 代码里还要区分 strong / weak：sp<IBinder> 会增加强引用，wp<IBinder> 不会；binderDied(const wp<IBinder>& who) 的参数是 weak，因为对象已经死了，不能再强引用它。这个细节在第 13 章讲引用计数时会展开。

另一个系统层例子是 ActivityManagerService（节选）。它为每个 app process 的 IApplicationThread 注册死亡通知：

private final class AppDeathRecipient implements IBinder.DeathRecipient {
    final ProcessRecord mApp;
    final int mPid;
    final IApplicationThread mAppThread;

    @Override
    public void binderDied() {
        if (DEBUG_ALL) Slog.v(TAG, "Death received in " + this);
        synchronized(ActivityManagerService.this) {
            appDiedLocked(mApp, mPid, mAppThread, true, null);
        }
    }
}
AppDeathRecipient adr = new AppDeathRecipient(app, pid, thread);
thread.asBinder().linkToDeath(adr, 0);
app.setDeathRecipient(adr);

真机上的 dumpsys activity processes 能看到 AMS 持有的 IApplicationThread$Stub$Proxy 和对应 PID：

adb shell "dumpsys activity processes | grep -A30 'ProcessRecord.*com.android.systemui' | grep -E 'ProcessRecord|thread=|pid=' | head -n 3"
  *PERS* UID 10044 ProcessRecord{5cf78e5 3741:com.android.systemui/u0a44}
    thread=android.app.IApplicationThread$Stub$Proxy@a68068d
    pid=3741

thread=...Stub$Proxy 就是这个进程的 Binder 代理；AppDeathRecipient 通过 linkToDeath 挂在这个代理上。进程死亡时，binderDied 触发 appDiedLocked，AMS 才开始清理进程记录。

六、把注册、回调和死亡通知串起来

把上面的源码串成一条时序。参与者是服务进程、servicemanager、回调客户端和 Binder 驱动：

服务进程 servicemanager 回调客户端 Binder 驱动
1. addService("demo", binder) 服务名和 IBinder 写入 IServiceManager.addService
2. binder->linkToDeath(ServiceManager) 服务进程死亡时回调 ServiceManager::binderDied
3. registerForNotifications("demo", cb) IServiceCallback 也是 oneway 接口
4. cb->onRegistration("demo", binder) 服务已注册时立即通知；oneway，不等客户端
5. 进程死亡，BR_DEAD_BINDER 驱动通知 linkToDeath 的接收者
6. binderDied() 清理 删除 mNameToService 和回调表中的条目

图由 CSS grid 生成；移动端会折叠成步骤列表。箭头方向以文字标签为准。

这条链解释了两个常见现象：服务进程崩溃后名字消失，以及回调客户端崩溃后 servicemanager 不会一直保留死 callback。两者都依赖同一个机制：linkToDeath + binderDied。

注册顺序也值得注意：如果 callback 先注册、服务后注册，addService 会通知 callback；如果服务先注册、callback 后注册，registerForNotifications 会在保存 callback 后立刻回调一次。无论顺序如何，客户端都不需要轮询；这也是系统服务常用“注册通知”而不是“反复查询”的原因。

七、源码阅读顺序

如果你准备自己读一遍，建议按下面的顺序，不要从 binder.c 开始：

  1. ServiceDebugInfo.aidl：最简单的一个系统 Parcelable。
  2. IServiceManager.aidl：registerForNotifications 和 getServiceDebugInfo 的声明。
  3. ServiceManager.cpp：addService、registerForNotifications、binderDied 三个函数。
  4. IServiceCallback.aidl 和生成的 IServiceCallback.java：看 oneway 和 callback 的客户端形态。
  5. IActivityManager.aidl / IPackageManager.aidl：找 out / inout 的真实方法。
  6. ActivityManagerService.AppDeathRecipient：看 app process 死亡通知如何接到 appDiedLocked。

读的时候始终带着一条主线：对象是谁、引用在哪里、谁负责在死亡后清理。AIDL 只是把这些关系编码成 Parcel 和事务。

八、系统层常见错误

错误后果 / 正确做法
用 service call 验证 onewayservice 不设置 FLAG_ONEWAY，仍然是同步事务；应读生成的 Proxy 或自己构造 flag。
给基本类型加 out / inoutAIDL 不允许；基本类型和小字符串默认是 in，多输出应使用 Parcelable 或 List。
Parcelable 字段顺序不一致Parcel 读错位，表现为异常、错字段或崩溃；客户端和服务端必须使用同一份 AIDL / 类版本。
callback 不 linkToDeath客户端进程退出后 callback 变成死 binder；servicemanager 的注册表会留下无效条目。
对本地 Binder 调 linkToDeath只有远程 binder 才需要死亡通知；服务端注册服务前会检查 binder->remoteBinder()。
忽略 SELinuxregisterForNotifications、getServiceDebugInfo 都受 canFind / canList 限制，失败时先看 avc。

九、动手练习

练习 1：解析 ServiceDebugInfo 数组

执行 adb shell 'service call manager 14'，把输出按 ServiceDebugInfo { String name; int debugPid; } 解析，列出前 5 个服务名和 debugPid。再和 service list 对比，说明为什么 debugPid 不能当实时 PID。

练习 2：找 out / inout 的真实接口

打开 IActivityManager.aidl 和 IPackageManager.aidl，找出 3 个带 out 或 inout 的方法，说明每个方法是“客户端写、服务端填、客户端读”中的哪一种。

练习 3：读 oneway 的生成代码

用 aidl --lang=java 生成 IServiceCallback.java，找到 onRegistration 的 Proxy。确认 transact 的最后一个参数带 IBinder.FLAG_ONEWAY，并解释为什么 service call 不能复现这条路径。

练习 4：跟踪死亡通知

读 ServiceManager::binderDied，列出它会清理的三种表：mNameToService、mNameToRegistrationCallback、mNameToClientCallback。再读 ActivityManagerService.AppDeathRecipient，说明 AMS 在 binderDied 后做了什么。

十、本章小结

  • 系统层的 Parcelable 是字段顺序协议，ServiceDebugInfo 可以在真机上用 service call manager 14 观察。
  • in / out / inout 描述 Parcel 的读写方向，主要用于 Parcelable、List、Map 等引用类型。
  • oneway 不等待 reply，callback 接口通常是 oneway；service call 不是验证 oneway 的工具。
  • servicemanager 用 IServiceCallback 做注册通知，用 linkToDeath + binderDied 清理服务和回调。
  • AMS 用同样的机制跟踪 app process 的 IApplicationThread；这是系统服务管理生命周期的核心手段。
