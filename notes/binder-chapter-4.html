第 4 章：
AIDL 进阶

第 3 章只传了一个 String。真实接口还会遇到自定义对象、方向标签、单向调用、回调和进程死亡。这一章把这几块补上，并给出可以继续扩展的代码骨架。

2026.11.15Binder 学习路线 · 第 4 章约 24 分钟动手实践

先把第 3 章的 Demo 扩展成一个更真实的接口：

interface IHelloService {
    String hello(String name);
    User getProfile(in User query);
    void registerCallback(IHelloCallback callback);
    void unregisterCallback(IHelloCallback callback);
    oneway void log(String message);
}

这里有五个新问题：

  • User 怎么跨进程？
  • in 是什么意思？还有 out / inout 呢？
  • oneway 什么时候用？
  • Callback 怎么从服务端反向调用客户端？
  • 服务端或回调进程死了，怎么知道？
✓
先给最重要的建议：能用一个返回值表达的结果，就不要用 out。方向标签会增加序列化成本，也会让接口和生成代码更难理解。初学阶段优先用“参数 in + 返回值”。

一、Parcelable：让自定义对象跨进程

AIDL 支持基本类型、String、List、Map、数组、IBinder、AIDL 接口和 Parcelable。自定义的 User 属于 Parcelable。

最简单的方式是用 Kotlin 的 @Parcelize：

// app/build.gradle.kts
plugins {
    id("com.android.application")
    id("org.jetbrains.kotlin.android")
    id("kotlin-parcelize")
}
// User.kt
package com.example.bindersample

import android.os.Parcelable
import kotlinx.parcelize.Parcelize

@Parcelize
data class User(
    val id: Int,
    val name: String
) : Parcelable

然后告诉 AIDL：这是一个 parcelable 类型。

// app/src/main/aidl/com/example/bindersample/User.aidl
package com.example.bindersample;

parcelable User;

在服务接口里导入它：

// IHelloService.aidl
package com.example.bindersample;

import com.example.bindersample.IHelloCallback;
import com.example.bindersample.User;

interface IHelloService {
    String hello(String name);
    User getProfile(in User query);
    void registerCallback(IHelloCallback callback);
    void unregisterCallback(IHelloCallback callback);
    oneway void log(String message);
}

服务端直接返回一个新的 User：

override fun getProfile(query: User): User {
    Log.d(TAG, "getProfile thread=${Thread.currentThread().name}")
    return User(query.id, "Hello, ${query.name}")
}
!
常见坑：AIDL 里使用自定义类型时，必须有对应的 User.aidl 声明，并在接口里 import。即使 User.kt 已经实现了 Parcelable，AIDL 编译器仍需要知道这是一个可序列化类型。

Parcelable 的字段顺序

@Parcelize 会根据主构造器自动生成 writeToParcel() 和 CREATOR。手写 Parcelable 时，读写的字段顺序必须完全一致，否则会出现数据错位或 BadParcelableException。

Android 10+ 的结构化 AIDL

也可以在 AIDL 里直接声明一个简单结构：

package com.example.bindersample;

parcelable User {
    int id;
    String name;
}

这适合纯数据传输对象；如果还需要自定义方法、校验或复杂逻辑，使用 Kotlin/Java 的 Parcelable 类更灵活。

二、in / out / inout

这三个方向标签描述的是数据在客户端和服务端之间怎么流动，不是“同步/异步”。

方向数据流适合注意
in客户端 → 服务端普通查询参数、Parcelable 请求对象服务端的修改不会带回客户端
out服务端 → 客户端需要填入多个结果客户端传入一个容器/对象，服务端负责填充；生成签名可能不直观
inout双向需要读入、修改、再返回的对象最贵；能用返回值就不要用它

基本类型、String、IBinder 和 AIDL 接口默认就是 in，不能改成 out / inout。方向标签主要用在 Parcelable、数组、List、Map 等类型上。

例如：

void fillUser(out User user);
void updateUser(inout User user);

对于新手，建议把这两个改成：

User fillUser();
User updateUser(in User user);

返回值方式语义更直接，也避免 out / inout 在不同 AIDL 后端和生成语言里的签名差异。确实需要多个输出时再使用方向标签。

三、oneway：不等待结果的调用

在 AIDL 里可以给方法加 oneway：

oneway void log(String message);

调用方发出事务后立即继续执行，不等待服务端返回结果。适合日志、通知、状态上报这类不需要 reply 的操作。

但要注意：

  • oneway 方法不能有返回值，也不能有 out / inout 参数。
  • “不等待结果”不等于“没有成本”：仍然要打包、入队、由服务端线程处理并释放 buffer。
  • 服务端异常通常不会以正常 reply 的形式返回；不要把它当成可靠投递。
  • 官方文档指出：本地调用使用 oneway 没有影响，仍然是同步的；oneway 只改变远程调用行为。
  • 大量 oneway 可能堆积，甚至触发 oneway spam 保护；关键业务要考虑限流和丢弃策略。

四、Callback：服务端反向调用客户端

Callback 的本质是：客户端把自己的 Binder 对象传给服务端，服务端拿到一个可以反向调用的代理。

1 / Register 客户端 registerCallback(callback)
2 / Store 服务端 保存 callback 代理
3 / Invoke 服务端 Binder 线程 调用 onGreeting()
4 / Client 客户端 Binder 线程 执行 Stub 回调
5 / UI 主线程 Handler / runOnUiThread

Callback 接口

// IHelloCallback.aidl
package com.example.bindersample;

oneway interface IHelloCallback {
    void onGreeting(String message);
}

使用 oneway 的原因是：服务端通知客户端通常不需要等待返回，避免服务端 Binder 线程被回调阻塞。

服务端保存 callback

private val callbacks = CopyOnWriteArrayList<IHelloCallback>()

override fun registerCallback(callback: IHelloCallback?) {
    if (callback == null) return
    callbacks.addIfAbsent(callback)
}

override fun unregisterCallback(callback: IHelloCallback?) {
    if (callback == null) return
    callbacks.remove(callback)
}

真实项目还应该处理 callback 进程死亡，避免一直持有一个已经失效的远程对象。后面 DeathRecipient 一节会补上。

客户端注册 callback

private val callback = object : IHelloCallback.Stub() {
    override fun onGreeting(message: String) {
        Log.d(
            TAG,
            "callback pid=${Process.myPid()} thread=${Thread.currentThread().name}"
        )
        runOnUiThread { resultText.text = message }
    }
}

在 onServiceConnected 里注册：

helloService = IHelloService.Stub.asInterface(binder)
try {
    helloService?.registerCallback(callback)
} catch (e: RemoteException) {
    Log.e(TAG, "registerCallback failed", e)
}

在 onDestroy 里反注册：

try {
    helloService?.unregisterCallback(callback)
} catch (e: RemoteException) {
    // 服务端可能已经死了
}
unbindService(connection)

Callback 运行在哪个线程？ 客户端的 Binder 线程，不是主线程。更新 UI 必须切回主线程。服务端调用 callback 时也会占用服务端自己的调用线程，因此不要假设回调会立即执行。

五、DeathRecipient：对象死了怎么办

Binder 调用可能遇到服务端进程崩溃、服务被移除等情况。除了 ServiceConnection.onServiceDisconnected，还可以直接对 Binder 注册死亡通知：

private val deathRecipient = IBinder.DeathRecipient {
    Log.w(TAG, "remote binder died")
    runOnUiThread { statusText.text = "服务端进程已退出" }
}

// onServiceConnected 里
binder.linkToDeath(deathRecipient, 0)

// 释放时
try {
    binder.unlinkToDeath(deathRecipient, 0)
} catch (e: NoSuchElementException) {
    // 已经死了
}

几个关键点：

  • binderDied() 通常不在主线程执行，更新 UI 要切线程。
  • 注册后要保存 DeathRecipient 引用，以便反注册。
  • onServiceDisconnected 和 linkToDeath 不是一回事：前者跟绑定连接有关，后者更接近“这个 Binder 对象死了”。
  • 服务端如果保存了客户端的 callback，也应该对 callback 的 binder 注册死亡通知，及时清理回调列表。

把这些能力串起来

一次完整的进阶调用可能长这样：

  1. 客户端绑定服务，拿到 IHelloService。
  2. 注册 IHelloCallback，服务端保存 callback 代理。
  3. 客户端传入 User，服务端返回新的 User。
  4. 服务端调用 callback，客户端 Binder 线程收到通知。
  5. 客户端用 Handler 切回主线程更新 UI。
  6. 服务端死亡，客户端 DeathRecipient 收到通知。

这一套就是很多系统服务回调、监听器、状态通知的简化版。

练习

  1. 给第 3 章的接口增加 User getProfile(in User query)，返回一个新对象。
  2. 增加 oneway void log(String message)，在服务端打印日志，确认客户端不等待返回值。
  3. 增加 IHelloCallback，让服务端在收到请求时通知客户端。
  4. 在 callback 里打印线程名，并用 runOnUiThread 更新 UI。
  5. 给服务 Binder 注册 DeathRecipient；从 adb 杀掉 :remote 进程，观察日志。
  6. 把某个 out User 方法改成返回 User，对比接口和实现的可读性。

自测题

1. Parcelable 和 Serializable 在 Binder 里有什么区别？

Binder/AIDL 使用 Parcelable 进行显式序列化。Serializable 依赖 Java 序列化机制，不适合作为 Binder 的跨进程数据契约。AIDL 自定义对象应实现 Parcelable，并声明对应的 .aidl 文件。

2. in / out / inout 分别是什么意思？

in 只从客户端传到服务端；out 由服务端填充后返回客户端；inout 双向。基本类型、String、IBinder 和 AIDL 接口默认是 in，不能改成 out/inout。

3. oneway 是“后台线程执行”吗？

不是。oneway 只表示调用方不等待回复；服务端仍然由 Binder 线程池处理，客户端服务端都可能需要线程和资源。

4. Callback 的方法运行在哪个线程？

客户端进程的 Binder 线程池线程。不能直接更新 UI，需要 Handler、runOnUiThread 或协程主线程调度。

5. DeathRecipient 和 onServiceDisconnected 有什么区别？

onServiceDisconnected 是 ServiceConnection 的回调，跟绑定关系有关；linkToDeath 直接监听某个 Binder 对象的死亡，适合监听回调对象或其他远程 Binder。

6. 为什么服务端要清理 callback？

callback 是客户端进程里的远程对象。客户端死亡后，如果服务端一直保存它，会持有无效引用并造成资源泄漏。可以对 callback 的 binder 注册 DeathRecipient，在死亡时移除。

7. 为什么建议用返回值代替 out 参数？

返回值语义明确，Parcel 只写回一次方向，生成的接口也更直观；out/inout 会增加序列化成本，而且不同 AIDL 后端/生成语言的签名可能让新手困惑。

本章小结

第 3 章解决“能跨进程调用”，第 4 章解决“能像真实接口一样工作”：

  • 用 Parcelable 传递结构化数据。
  • 用 in / out / inout 控制数据方向，但优先用返回值。
  • 用 oneway 做不等待的通知。
  • 用 callback 让服务端反向通知客户端。
  • 用 DeathRecipient 处理对象或进程死亡。
