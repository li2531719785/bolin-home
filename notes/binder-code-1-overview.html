这次调用是怎么发起的

调用方要执行 ActivityManager 的某个方法。AIDL 生成的 Stub.Proxy 先把参数写进 Parcel，填上方法编号 code，再调用 BinderProxy.transact。对调用方来说，这只是一次普通方法调用；对 Binder 来说，一次跨进程调用已经打包好，准备交给下一层。

Java 层只是入口的壳。真正决定数据怎么排队、怎么进驱动、对端怎么被唤醒的，是 native 侧的 BpBinder 和内核里的 binder.c。所以这条路线不从 Java 开始，而是先读本体，把 Java/JNI 放到第 6 章收尾。

六章地图

用户代码（调用方）
└─ AIDL Stub.Proxy           // AIDL 生成，填 Parcel        ← 第 6 章
    └─ BinderProxy.transact  // Java 框架入口               ← 第 6 章
        └─ JNI transact      // Java→C++ 的桥               ← 第 6 章
            └─ BpBinder::transact  // native 代理           ← 第 2 章
                └─ IPCThreadState   // 打包、ioctl 进驱动   ← 第 2 章
                    └─ binder.c 驱动 // 找到目标、唤醒对端   ← 第 3 章
                        └─ 服务端 onTransact → 回填 reply    ← 第 4 章

第 5 章是横切：服务怎么注册、怎么查找。第 3 章会把驱动数据结构并进来，读的时候可以配合 《Android Binder 驱动数据结构关系》 的交互图。

名词一句话速查

code
接口方法的编号，AIDL 里每个方法一个 int。
data / reply
序列化的信封：data 装参数，reply 由对端填返回值。
flags
同步调用会阻塞等回复；FLAG_ONEWAY 表示不等待回复。
BpBinder
Bp = Binder Proxy，是 Java BinderProxy 在 native 侧的真实对象。
JNI
Java 调 C++ 的转换桥，负责把 Java 对象转成 native 指针。
handle
native 侧的数字句柄，进程内用它索引 binder_ref。
驱动
drivers/android/binder.c，负责找到目标进程、把事务放上队列、唤醒接收线程。
