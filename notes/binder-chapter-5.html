第 5 章：
ServiceManager 与服务注册

第 3、4 章的服务都由 App 自己 bindService：客户端知道组件名，AMS 负责把连接建起来。系统服务不是这个模型。system_server 启动时先把 AMS、PMS、WMS 登记到一个“总台”，客户端只拿名字去查。这个总台就是 servicemanager。

2026.11.16Binder 学习路线 · 第 5 章约 26 分钟Framework

这一章只回答一件事：一个字符串名字，怎么变成一个可以调用的 Binder 代理？ 沿途会遇到 servicemanager、handle 0、context manager、addService / getService，以及一个很容易被误解的问题：handle 到底是不是全局编号。

✓
先记住一句话：ServiceManager 是电话簿，不是交换机。它负责把名字换成 Binder 引用；真正的跨进程调用不经过它。

一、先解决一个死结：系统服务找谁登记

普通 App 的 Service 有一套完整的组件模型：在 Manifest 里声明，用 bindService() 绑定，AMS 负责找到进程、创建服务，再把 onBind() 返回的 IBinder 通过 onServiceConnected() 交给客户端。

但系统服务启动得更早，而且没有“组件名”可以查。更麻烦的是：AMS 自己也是要被登记的服务之一。如果查服务必须先有 AMS，而 AMS 又要先被别人查到，就形成了死结。

所以需要一个不依赖其他服务的固定入口：

  • 它在系统启动早期就运行；
  • 所有进程都知道怎么找到它；
  • 它只维护“名字 → Binder 引用”的映射；
  • 它自己也是一个 Binder 服务。

这就是 servicemanager。它由 init 启动，是一个独立的 native 进程，不是 system_server 的一部分。大致的启动顺序是：

init
  → servicemanager       // 先建立“总台”
    → zygote
      → system_server    // 再把 AMS / PMS / WMS 等登记进去

system_server 启动时会调用 ServiceManager.addService() 把系统服务逐个发布出去。之后 App 通过 getSystemService() 拿到的管理器，很多最终都对应到这些已登记的服务。

!
它不在每次调用的数据路径上。客户端只在“查名字”时访问 servicemanager；拿到 Binder 代理后，后续方法调用直接发给服务进程。servicemanager 的压力主要来自启动时的注册和查找，而不是业务请求。

二、servicemanager 与 handle 0

servicemanager 启动后会做三件事：打开 Binder 设备、把设备映射到自己的地址空间、告诉驱动“我是这个 Binder 上下文的 context manager”。第三步是老代码里最直观的一行：

ioctl(bs->fd, BINDER_SET_CONTEXT_MGR, 0);

驱动收到这个 ioctl 后，会为 servicemanager 创建一个 binder_node，并把它记录在对应 Binder 上下文的 binder_context 里。这个 node 就是“总台”在内核里的身份。

同一个 Binder 上下文只能有一个 context manager。第二次设置通常会失败；不同 euid 的进程来抢，也会被拒绝。这个限制很重要，否则“handle 0 指向谁”就没有唯一答案了。

1 / init init 启动 servicemanager
2 / Open servicemanager open("/dev/binder") + mmap
3 / Register Binder 驱动 BINDER_SET_CONTEXT_MGR
4 / Node binder_context 记录 context manager node
5 / Handle 0 所有进程 handle 0 → 这个 node

从这以后，任何进程只要打开了同一个 Binder 设备，handle 0 就代表 servicemanager。当驱动处理一个目标 handle 为 0 的事务时，不需要查普通的 ref 表，而是直接使用 binder_context 里保存的 context manager node。

名字是什么容易误解的地方
handle 0每个进程里指向 context manager 的保留索引不是 PID，也不是全局唯一的服务编号；它只在当前进程和当前 Binder 上下文里有意义
binder_node内核里代表一个 Binder 对象服务进程注册后，node 才是对象的“真身”；客户端拿到的是引用
binder_ref某个进程对某个 node 的引用handle 是这个 ref 在该进程里的编号，不同进程可以不同
svcinfoservicemanager 保存的注册表项里面存的是 servicemanager 自己视角下的 handle，不是客户端的 handle
BpBinder客户端侧指向某个 handle 的代理它只是“遥控器”，不包含服务实现
!
handle 0 是约定，不是特权编号。它之所以特殊，是因为驱动在目标 handle 为 0 时走 context manager 分支。你自己注册的服务不会被分配成 0；0 永远留给“总台”。

三、addService：把本地对象登记成名字

先看服务端。一个系统服务通常会持有一个本地 Binder 对象，例如 Java 里的 Stub 子类，或者 native 里的 BBinder 子类。注册时，它把这个对象的引用和名字一起发给 servicemanager。

Java 侧（system_server / framework 内部）大致是这样：

// 仅示意：普通 App 不能这样注册系统服务
ServiceManager.addService("demo", new DemoService());

Native 侧：

sp<IServiceManager> sm = defaultServiceManager();
sp<IBinder> service = new DemoService();   // DemoService 继承 BBinder
status_t err = sm->addService(String16("demo"), service);

addService() 不是往本地 HashMap 里写一条记录，而是一次真正的 Binder 事务：客户端把目标设为 handle 0，事务码是 ADD_SERVICE，Parcel 里包含服务名、Binder 对象和若干标志位。

1 / Local 服务进程 new DemoService()
2 / Add libbinder addService("demo", binder) → handle 0
3 / Translate Binder 驱动 本地对象 → node；为 servicemanager 建 ref
4 / Store servicemanager 记录 name → handle + death
5 / Reply 注册完成 服务继续运行

关键在第 3 步。服务进程传给 addService 的是本地 Binder 对象，Parcel 里的类型是 BINDER。驱动会为它创建（或复用）一个 binder_node，然后在 servicemanager 的进程里创建一个 binder_ref，并分配一个 handle。servicemanager 最终保存的是：

  • 服务名，例如 "activity"；
  • 它自己进程里的 handle；
  • 死亡通知的 cookie，用来在服务进程退出时删掉表项；
  • 一些访问标志，例如是否允许 isolated 进程查找。

所以注册表里的 handle 只对 servicemanager 有意义。其他客户端来查时，驱动会重新为它们创建引用，handle 值可能完全不同。

注册不是永久有效

servicemanager 会在注册时登记死亡通知。服务进程退出后，驱动通知 servicemanager，对应的表项会被移除。客户端如果还缓存着旧的代理，后续调用会得到 DeadObjectException（Java）或 DEAD_OBJECT（native），需要重新查找或处理死亡通知。

哪些名字会出现在这里

服务名注册者说明
activitysystem_serverActivityManagerService，对应 IActivityManager
packagesystem_serverPackageManagerService，对应 IPackageManager
windowsystem_serverWindowManagerService，对应 IWindowManager
SurfaceFlingerSurfaceFlinger 进程native 服务，图形合成的核心
media.playermediaserver 进程native 媒体服务，不是 system_server 里的 Java 对象

这张表说明：servicemanager 不只服务 Java 系统服务。native 进程、HAL、甚至厂商自己的守护进程，都可以在同一个 Binder 上下文里注册名字。

四、getService：把名字换成一个代理

客户端查找服务时，目标同样是 handle 0。Java 侧常见写法：

IBinder binder = ServiceManager.getService("activity");
IActivityManager am = IActivityManager.Stub.asInterface(binder);

Native 侧：

sp<IServiceManager> sm = defaultServiceManager();
sp<IBinder> binder = sm->getService(String16("demo"));
sp<IDemoService> demo = interface_cast<IDemoService>(binder);
1 / Lookup 客户端 getService("demo") → handle 0
2 / Find servicemanager 按名字查注册表
3 / Reply Binder 驱动 把服务对象放进 reply
4 / Translate 客户端进程 创建新的 ref / handle
5 / Proxy BpBinder interface_cast → BpDemoService

查完之后，servicemanager 就退场了。客户端拿到的是服务进程的 Binder 引用，之后调用 demo->hello() 会直接把事务发给服务进程，不再经过 servicemanager。

同一个服务，不同进程看到的 handle 可能不同

下面这张表是示意，不是某台设备上的真实编号：

进程它看到的 activity原因
system_server本地 ActivityManagerService 对象它是注册者，自己持有实现，不需要通过 handle 调用
servicemanagerhandle 3（示意）注册时驱动为它创建的 ref
App Ahandle 12（示意）查找时驱动为 App A 创建的 ref
App Bhandle 7（示意）另一个进程，另一张 ref 表，编号可以不同

它们指向的是同一个 binder_node，但 handle 只是各自进程里的索引。这就是为什么不能把 handle 当成全局 ID 传给另一个进程。

缓存：名字只查一次

Java 的 ServiceManager 有一个静态缓存，专门保存常见的系统服务代理；native 的 ProcessState 也会按 handle 缓存 BpBinder。所以“每次调用都去问 servicemanager”并不成立：通常只在进程第一次查找（或缓存失效）时发生一次 IPC。

但缓存的是代理，不是服务实现。服务进程死亡后，代理会失效；缓存本身不会让旧代理复活。需要重新获取服务，或者用 DeathRecipient 做失效处理。

getService、checkService、waitForService 不是一回事

API行为适合场景
getService(name)按名字查找；Java 实现未命中时返回 null，不会自动把服务拉起来服务已经确定注册，且调用方可以处理 null
checkService(name)明确的非阻塞查找；未注册就返回 null服务可能不存在，调用方自己决定重试或降级
waitForService(name)面向“已声明、可懒启动”的服务；servicemanager 可能请求启动它并等待就绪HAL / lazy service，启动顺序不确定时
getSystemService(name)从 SystemServiceRegistry 取管理器对象，可能本地，也可能内部持有 Binder 代理App 获取系统能力的常规方式
!
同名 API 在不同层的行为不一样。libbinder 的 getService() 在找不到时会重试一段时间（现代实现大约 5 秒，旧实现是若干次 1 秒轮询）；Java 的 ServiceManager.getService() 更接近一次 checkService()。读源码时先确认自己看的是哪一层，不要拿一个结论套所有调用。

五、getSystemService 背后是什么

App 通常不会直接调用 ServiceManager.getService("activity")，而是：

ActivityManager am = (ActivityManager) getSystemService(Context.ACTIVITY_SERVICE);

这条路径大致是：

Context.getSystemService(name)
  → SystemServiceRegistry 查 name 对应的 ServiceFetcher
    → 创建 / 取出管理器对象
      → 管理器内部持有或获取 Binder 代理

所以“getSystemService 背后一定能找到一个远程 Binder”也不准确。它返回的是客户端管理器，可能只是一个本地 helper；只有当这个管理器需要跨进程时，才会出现 Binder 代理。

调用背后的服务实际位置
getSystemService(Context.ACTIVITY_SERVICE)activity / IActivityManagersystem_server
getSystemService(Context.WINDOW_SERVICE)window / IWindowManagersystem_server；返回的是客户端侧的 WindowManager
getPackageManager()package / IPackageManagersystem_server
getSystemService(Context.LAYOUT_INFLATER_SERVICE)无 Binder 服务本地 LayoutInflater
✓
别把 SystemServiceManager 和 ServiceManager 搞混。前者在 system_server 内部管理服务的生命周期（onStart、onBootPhase）；后者才是 Binder 名字注册表。名字很像，职责完全不同。

六、三个 servicemanager

“servicemanager”经常被当成一个东西，其实 Android 里至少有三种 Binder 上下文，各自有一个 context manager：

Binder 设备Context manager主要用途
/dev/binderservicemanagerFramework 系统服务、AIDL HAL、普通 Binder 服务
/dev/hwbinderhwservicemanagerHIDL HAL（历史实现；新 HAL 优先用 AIDL）
/dev/vndbindervndservicemanagerVendor 进程之间的 Binder 服务

它们是三个独立的上下文。每个上下文都有自己的 handle 0，也都有自己的注册表。一个进程可以同时打开多个 Binder 设备，但不要把 A 设备上的 handle 拿去 B 设备使用。

AIDL HAL 和 HIDL HAL 的注册位置也不同。HIDL 时代的 HAL 通过 hwservicemanager 按 FQName 查找；AIDL HAL 通常注册到 servicemanager（或 vendor 侧的 vndservicemanager），用实例名区分。具体走哪条路径，要看进程打开的是哪个 Binder 设备。

七、安全边界：为什么普通 App 不能注册

android.os.ServiceManager 的类注释写得很直接：这些服务必须静态声明在设备上（SELinux 的 service_manager 访问向量，服务名在 service_contexts 里），并且不遵循 Activity 的生命周期；“构建应用时，应该优先使用 android.app.Service”。

注册和查找至少要过两道门：

  1. servicemanager 的用户态检查。它通过 SELinux 的 service_manager 类检查调用者有没有 add 或 find 权限，检查对象是服务名对应的 SELinux 类型。
  2. Binder 驱动的内核检查。真正发起事务时，还要有进程之间的 binder { call } 权限；传递 Binder 对象时还会涉及 transfer。设置 context manager 本身也受 set_context_mgr 权限约束。

因此，普通 App 即使用反射调用 ServiceManager.addService()，也会因为 hidden API 限制和 SELinux 拒绝而失败。普通 App 的 Service 走的是另一条路：Manifest 声明 + bindService()，由 AMS 管理连接，根本不会出现在 servicemanager 的注册表里。

allowIsolated 和 dumpPriority 这些参数也不是“绕过安全检查”的开关。前者只决定 isolated 进程能不能查找，后者影响 dumpsys 的优先级。

!
服务名也是 ABI 和安全策略的一部分。改名字不只是改一个字符串：客户端、SELinux 的 service_contexts、允许规则都要一起改。新增系统服务时，通常需要同时补 sepolicy，否则注册或查找会直接被拒绝。

八、常见误解

说法实际情况
handle 0 是 servicemanager 的 PID不是。handle 是进程内的索引；0 只是 context manager 的保留值
handle 是全局唯一编号不是。同一个服务在不同进程可以有不同 handle，指向同一个 node
每次 Binder 调用都要经过 servicemanager不是。它只参与查找；拿到代理后调用直接到服务进程
servicemanager 就是 system_server不是。两个独立进程；system_server 是 servicemanager 的客户端
getService() 一定会等 service 启动Java 层未命中会返回 null；要等已声明的 lazy service，用 waitForService()
getSystemService() 每次都会 IPC不一定。它取的是管理器对象，可能是本地 helper，也可能缓存了代理
普通 App 也能 addService()不能。hidden API + SELinux + 静态声明要求；App 应使用 bindService()

九、动手观察

不需要改代码，先用 adb 看清系统里的角色分工。不同 Android 版本的输出格式可能略有差异。

# 1. 看两个进程是不是独立的
adb shell ps -A | grep -E "servicemanager|system_server"

# 2. 看注册表里有哪些名字
adb shell service list | grep -E "activity|package|SurfaceFlinger|media.player"

# 3. 检查某个服务是否存在
adb shell service check activity

# 4. 看 dumpsys 认识的服务
adb shell dumpsys -l | head -n 20

# 5. 看 Binder 设备
adb shell ls -l /dev/binder /dev/hwbinder /dev/vndbinder

预期结果：

  • servicemanager 和 system_server 是两个不同 PID；前者通常更早启动。
  • service list 里能看到 activity、package、SurfaceFlinger 等名字。
  • service check activity 会报告找到服务；如果服务尚未注册，则报告未找到。
  • 部分设备可能没有 /dev/hwbinder 或 /dev/vndbinder，这不代表系统有问题，取决于平台配置。

还可以观察 servicemanager 映射的 Binder 设备：

adb shell cat /proc/$(pidof servicemanager)/maps | grep binder

如果 pidof 不可用，先用 ps -A | grep servicemanager 找到 PID，再替换命令里的 $(pidof ...)。

十、自测题

1. 为什么 servicemanager 要在 zygote / system_server 之前启动？

因为 system_server 一启动就要把 AMS、PMS 等服务发布出去，而这些服务需要一个已经存在的“总台”来接收注册。servicemanager 先运行并成为 context manager，handle 0 才有确定的目标；否则系统服务无法完成名字登记。

2. handle 0 为什么特殊？它是全局唯一编号吗？

handle 0 是每个进程中留给 context manager 的保留索引。驱动在处理目标 handle 为 0 的事务时，直接使用 binder_context 里的 context manager node，而不是查普通 ref 表。它不是全局编号，也不是 PID；同一个 handle 值在不同进程里可能代表不同对象。

3. addService 时，驱动做了什么？servicemanager 存的是什么？

服务进程把本地 Binder 对象放进 Parcel，驱动为它建立 binder_node，并在 servicemanager 进程里创建 binder_ref 和 handle。servicemanager 保存服务名、自己视角下的 handle、死亡通知 cookie 和访问标志。它存的不是服务进程的指针。

4. getService 之后，实际方法调用还会经过 servicemanager 吗？

不会。getService 只完成一次“名字 → Binder 引用”的解析；客户端拿到代理后，后续调用直接把事务发给服务进程。servicemanager 不在业务调用的数据路径上。

5. getService、checkService、waitForService 有什么区别？

getService 是按名字查找（Java 层未命中返回 null；native 层可能重试一段时间）；checkService 是明确的非阻塞查找；waitForService 面向已声明、可懒启动的服务，servicemanager 可能请求启动并等待就绪。三者不要混用。

6. 普通 App 能不能调用 ServiceManager.addService？

不能。ServiceManager 是 hidden / SystemApi，普通 App 编译和反射都会受限；更重要的是 SELinux 的 service_manager add 会拒绝，服务名还必须静态声明。App 应该使用 Manifest 里的 Service 加 bindService()。

7. servicemanager、hwservicemanager、vndservicemanager 怎么分工？

它们分别是 /dev/binder、/dev/hwbinder、/dev/vndbinder 三个上下文的 context manager。servicemanager 管 framework 和常见的 AIDL 服务；hwservicemanager 管 HIDL HAL；vndservicemanager 管 vendor 侧服务。每个上下文都有自己的 handle 0 和注册表。

8. getSystemService 和 ServiceManager.getService 是一回事吗？

不是。ServiceManager.getService 直接按名字取原始 IBinder；getSystemService 走 SystemServiceRegistry，返回客户端管理器对象，可能完全在本地，也可能在内部持有 Binder 代理。

本章小结

  • servicemanager 是启动早期的“电话簿”，解决系统服务名字查找的鸡生蛋问题。
  • 它通过 BINDER_SET_CONTEXT_MGR 成为 context manager；在同一个 Binder 上下文中，handle 0 都指向它。
  • addService 把本地 Binder 对象登记成名字；驱动负责 node / ref 的转换，servicemanager 保存自己视角下的 handle。
  • getService 只做一次解析；之后调用直接到服务进程，handle 是进程内索引，不是全局 ID。
  • 普通 App 的服务走 bindService + AMS，不进入 servicemanager；系统服务还要受 SELinux 和静态声明约束。

下一章会回到用户态，把 IBinder、BpBinder、BBinder、Java 的 Binder 和 BinderProxy 放在一起，解释“同一个服务、不同 handle”在对象模型里到底怎么对应。
