第 0 章：Binder 的
预备知识

很多人学 Binder 卡住，不是因为 Binder 本身，而是因为进程、虚拟内存、文件描述符和系统调用这些前置概念不牢。本章不碰 Binder 源码，只把进入 Binder 之前必须有的直觉补齐。

2026.11.17Binder 学习路线 · 第 0 章约 18 分钟基础篇

这一章的目标不是让你记住名词，而是能回答一个核心问题：为什么一个进程不能直接调用另一个进程里的函数？ 把这个问题想明白，后面的 Binder、handle、transaction、buffer 才有落脚点。

✓
学完本章，你应该能：说清进程隔离和虚拟内存；解释线程共享什么；知道 fd、ioctl、mmap 各自负责什么；能画出 Android 里 zygote、system_server、servicemanager 和 app 的基本关系；并知道 Binder 为什么需要内核驱动。

本章地图

  • 进程：资源隔离的容器。
  • 线程：真正被 CPU 执行的单位，同一进程的线程共享地址空间。
  • 虚拟内存：每个进程都有自己的地址空间，指针不能跨进程直接使用。
  • 文件描述符：进程内的编号，不是全局资源 ID。
  • 系统调用：用户态进入内核的唯一受控入口。
  • ioctl / mmap：Binder 与内核驱动交互的两个关键入口。
  • Parcel：跨进程传递数据的序列化载体。
  • Android 进程模型：zygote、system_server、servicemanager 与 app。

1. 进程：隔离的资源容器

进程可以理解为“一个正在运行的程序实例”。它拥有自己的虚拟地址空间、文件描述符表、权限凭据、信号处理状态等资源。操作系统把不同进程隔离开，一个进程不能随意读写另一个进程的内存。

Android 里每个 app 通常运行在独立进程中，拥有自己的进程 ID（PID）和地址空间。即使两个进程运行同一份 APK 代码，它们的内存也不是共享的。

这带来一个重要结论：

你在 A 进程里拿到一个对象指针，把它发给 B 进程，B 进程不能直接解引用它。因为这个地址在 B 的地址空间里可能根本不存在，或者指向完全不同的东西。

跨进程调用不能靠“传指针”，必须把“调用哪个对象、执行什么方法、参数是什么”翻译成双方都能理解的描述，再交给内核搬运。这就是 Binder 要解决的问题。

进程和 Binder 的对应关系

Binder 驱动会为每个打开 /dev/binder 的进程维护一个 binder_proc。你可以先把它理解成“这个进程的 Binder 档案”：它保存该进程的线程、拥有的 Binder 对象、引用关系、待处理工作等。

2. 线程：真正执行代码的单位

线程是 CPU 调度的基本单位。一个进程至少有一个线程；同一个进程里的多个线程共享地址空间、堆、全局变量和文件描述符表，但每个线程有自己的栈、寄存器和程序计数器。

资源同一进程的线程不同进程
虚拟地址空间共享隔离
堆 / 全局变量共享不共享
文件描述符表共享独立
线程栈 / 寄存器各自独立各自独立

Binder 里“线程”非常重要：同步调用会阻塞发起调用的线程；服务端由某个 Binder 线程接活；transaction_stack 也是按线程保存的。所以看到一个 Binder 调用时，要同时问两个问题：

  • 它是从哪个进程发起的？
  • 它是从哪个线程发起的？

3. 虚拟内存：地址不是共享的

现代操作系统使用虚拟内存。每个进程都以为自己拥有一整片连续地址空间，但实际上这些虚拟地址会被页表映射到不同的物理内存页。

进程 A 的虚拟地址 0x1000  ──┐
                            ├──▶ 物理页 X
进程 B 的虚拟地址 0x1000  ──┘

同样的虚拟地址，可能映射到同一块物理页，
也可能映射到完全不同的物理页。

所以“把指针发过去”没有意义。两个进程的 0x1000 不是同一个东西。跨进程传数据，必须经过复制、序列化或者显式的共享内存映射。

mmap 是什么

mmap 是内存映射系统调用：它把文件、设备或一段匿名内存映射到进程的虚拟地址空间。映射之后，进程可以像访问普通内存一样访问这块区域。

Binder 也会使用 mmap：每个进程可以把自己的一块虚拟地址区域映射给 Binder 驱动，用来存放 Binder buffer。接收方最终通过自己进程里的映射地址读取数据。

这里先记住一句话：

Binder 的数据最终落在接收方进程的 Binder 缓冲区里，而不是发送方的堆上。

“Binder 是一次拷贝”这个说法，指的是数据从发送方用户缓冲区复制到接收方 Binder buffer 的过程；它不是“零拷贝”，也不是把发送方指针直接交给接收方。具体细节留到驱动章节再看。

4. 文件描述符：fd 只是进程内编号

在 Linux 里，打开文件、设备、管道或 socket 都会得到一个文件描述符（file descriptor，简称 fd）。它是一个非负整数，比如 0、1、2 分别通常是标准输入、标准输出、标准错误。

关键点：fd 是进程内文件描述符表的下标，不是全局 ID。A 进程的 fd 7 和 B 进程的 fd 7 很可能指向完全不同的文件对象。

进程 A 的 fd 表          进程 B 的 fd 表
0 → stdin                 0 → stdin
1 → stdout                1 → stdout
2 → stderr                2 → stderr
3 → /dev/binder           3 → 某个 socket
7 → 一张图片              7 → 另一个文件

Binder 驱动也是通过一个字符设备暴露给用户态的，通常就是 /dev/binder。用户态打开它，拿到一个 fd，之后通过这个 fd 发 ioctl 命令与驱动交互。

Binder 还支持在事务中传递 fd。因为 fd 只在原进程里有意义，驱动需要在目标进程里“安装”一个新的 fd，指向同一个内核文件对象。这就是后面会看到的 fd fixup 机制。

5. 系统调用：从用户态进入内核

用户态程序不能直接执行特权指令，也不能直接访问内核数据结构。要读文件、发网络包、申请内存、与设备通信，必须通过系统调用进入内核。

一次系统调用大致经历：

  1. 用户态准备参数，执行特定的 CPU 指令进入内核。
  2. 内核根据系统调用号分发到对应处理函数。
  3. 内核完成操作，把结果返回用户态。

Binder 的用户态库最终也会落到系统调用。你不需要在本章记住具体的汇编入口，只需要理解：跨进程通信不是两个用户态进程直接对话，而是双方都通过系统调用与内核里的 Binder 驱动交互。

6. ioctl 与 mmap：Binder 的两个关键入口

ioctl：发命令

ioctl（input/output control）是一种通用的设备控制系统调用。它的典型形式是：

ioctl(fd, request, arg);
  • fd：打开的设备文件描述符，比如 /dev/binder。
  • request：命令号，告诉驱动要做什么。
  • arg：参数指针，通常指向一块用户态结构体。

Binder 最核心的命令之一是 BINDER_WRITE_READ：用户态通过它把“要发送的事务”和“要读取的返回结果”一起交给驱动。

可以把它理解成：

用户态：我要发一个 Binder 调用，同时请把新的返回结果给我
   │
   ▼
ioctl(binder_fd, BINDER_WRITE_READ, &bwr)

mmap：准备接收区域

mmap 负责把一个 Binder 内存区域映射到当前进程。它更像“准备一块收件区域”，而不是每次调用都重新分配。

两者分工可以先粗略记成：

入口作用Binder 里的角色
open打开设备，获得 fd打开 /dev/binder
mmap建立内存映射映射 Binder buffer 区域
ioctl发送控制命令收发事务、管理引用、线程状态

真正的事务数据会通过 ioctl 里的描述信息被内核处理，并复制到接收方的 Binder buffer 中；接收方再通过自己映射的地址读取。

7. Parcel：跨进程数据怎么打包

既然不能传指针，跨进程参数就必须被序列化。Android 里最常用的载体叫 Parcel。

Parcel 可以写入基本类型、字符串、数组、Parcelable 对象等。它既有 Java 层实现，也有 Native 层实现。AIDL 生成的 Proxy / Stub 会自动把方法参数写入 Parcel，再在服务端读出来。

客户端调用：
  proxy.getUser(id, callback)

AIDL 生成的 Proxy：
  data.writeInt(id)
  data.writeStrongBinder(callback)
  transact(GET_USER, data, reply, 0)

服务端 Stub：
  id = data.readInt()
  callback = data.readStrongBinder()
  getUser(id, callback)

你不需要现在就会手写 Parcel。先记住：Parcel 负责把“参数”变成一段可搬运的字节，同时保留对象引用信息。它不是简单的 JSON，也不是把内存直接拷过去就完事。

8. Android 进程模型：谁在和谁说话

Android 的进程世界可以先搭一个粗略骨架：

Linux 内核
  ├── init
  │    ├── servicemanager
  │    └── zygote
  │         ├── system_server
  │         └── 普通进程（按需 fork）
  └── Binder driver

zygote：app 的孵化器

zygote 会预先加载 Android 运行时和常用类库，然后通过 fork 创建新的 app 进程。这样新进程不需要每次从零启动，能更快进入应用代码。

system_server：系统服务的大本营

system_server 是一个非常重要的进程，里面运行着 ActivityManagerService、PackageManagerService、WindowManagerService 等大量系统服务。客户端进程调用系统能力时，很多请求最终都会走到 system_server 中的某个 Binder 服务。

servicemanager：服务名字的登记处

服务端需要把自己注册到 ServiceManager，客户端才能通过服务名查找到对应的 Binder 引用。你可以先把它理解成“服务通讯录”。后面会专门讲 handle 0 和 ServiceManager 的细节。

app process：普通应用进程

普通进程既可能是 Binder 客户端，也可能是 Binder 服务端。比如一个进程实现了 AIDL 服务，另一个进程就可以通过 Binder 调用它；同一个进程也可能在调用系统服务，成为别人的客户端。

9. 把概念拼成 Binder 的全景

现在把前面所有概念放到一张图里：

进程 A（客户端）                         进程 B（服务端）
┌─────────────────────┐                 ┌─────────────────────┐
│ Java / Native 代码   │                 │ Stub / 实际服务代码   │
│ BinderProxy         │                 │ BBinder              │
└─────────┬───────────┘                 └─────────▲───────────┘
          │ ioctl(BINDER_WRITE_READ)              │
          ▼                                       │
┌─────────────────────────────────────────────────────────────┐
│                     Binder 驱动（内核态）                     │
│  解析 handle → 找到 node → 分配目标 buffer → 投递 work 项      │
└─────────────────────────────────────────────────────────────┘
          │                                       ▲
          │ 数据复制到 B 的 Binder buffer           │ B 的 Binder 线程读取
          ▼                                       │
      B 进程的 mmap 区域  ────────────────────────┘

这张图里已经出现了后续会反复见到的对象：代理、Binder 实体、handle、node、buffer、事务和线程。但你现在只需要抓住主线：

  1. A 通过 fd 和 ioctl 把调用交给驱动。
  2. 驱动把 handle 解析成 B 进程里的 Binder 对象。
  3. 驱动把参数放进 B 进程的 Binder buffer。
  4. B 的 Binder 线程读取并执行，然后把结果沿反方向送回。

更细的结构、队列和引用计数会在第 10–13 章展开。

10. 动手实验

下面这些命令只需要一台开启了 USB 调试的 Android 设备或模拟器，以及 adb。不要修改系统设置，观察即可。

实验 1：看 Android 的关键进程

adb shell ps -A | grep -E "zygote|system_server|servicemanager"

你应该能看到 zygote、system_server 和 servicemanager。记下它们的 PID。

实验 2：看系统服务列表

adb shell service list | head -n 30
adb shell dumpsys -l | head -n 30

这些名字背后都是注册在 Binder 体系里的服务。现在不需要知道每个服务做什么，先建立“系统里有很多 Binder 服务”的感觉。

实验 3：观察 shell 进程自己的地址空间和 fd

adb shell cat /proc/self/status | grep -E "Pid|Tgid|VmSize|VmRSS"
adb shell ls -l /proc/self/fd

/proc/self 指向当前 shell 进程。看看它的 fd 表：0、1、2 通常已经存在，还可能有一些 pipe 或 socket。记住这些数字只属于当前进程。

实验 4：画图

不看笔记，画一张图，包含：

  • 进程 A 和进程 B
  • 各自的用户态 / 内核态边界
  • /dev/binder、ioctl、mmap
  • Binder 驱动
  • 一条从 A 到 B 的调用箭头

如果能把这张图画出来，第 0 章就达标了。

11. 自测题

先自己回答，再展开对照。

1. 为什么 A 进程不能把对象指针直接传给 B 进程？

因为每个进程有独立的虚拟地址空间。同一个虚拟地址在两个进程里可能映射到不同物理页，甚至没有映射。指针只在所属进程的地址空间里有意义。

2. 同一进程的线程共享什么？不共享什么？

共享虚拟地址空间、堆、全局变量和文件描述符表；各自拥有线程栈、寄存器和程序计数器。Binder 同步调用会阻塞发起调用的那个线程，而不是整个进程的所有线程。

3. A 进程的 fd 7 和 B 进程的 fd 7 是同一个东西吗？

不是。fd 是进程文件描述符表的下标，只在所属进程内有意义。两个 fd 数字相同，不代表指向同一个文件对象。

4. ioctl 和 mmap 在 Binder 里分别负责什么？

mmap 负责把一块 Binder 内存区域映射到进程地址空间；ioctl 负责发送控制命令和事务，最核心的是 BINDER_WRITE_READ。一个准备内存，一个负责通信控制。

5. 为什么 Binder 需要内核驱动？

因为跨进程通信需要内核做隔离边界内的事情：解析 handle、找到目标对象、把数据复制到目标进程的 buffer、排队和唤醒线程、检查权限，并处理对象引用和死亡通知。用户态进程无法直接完成这些操作。

6. Parcel 是“把内存直接拷过去”吗？

不是。Parcel 是序列化容器：它把参数按约定写成一段字节，并在需要时记录 Binder 对象等特殊信息。接收端再按同样的规则读出来。它解决的是“数据怎么表达”，不是简单复制指针。

7. zygote、system_server、servicemanager 各是什么？

zygote 是 app 进程的孵化器；system_server 运行大量系统服务；servicemanager 是服务注册和查找的通讯录。普通 app 通过 Binder 与这些进程中的服务交互。
