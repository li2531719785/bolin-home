00 Mental Model

先记住这个比喻，再进入结构

Binder 并不把对象“复制”到另一个进程。它在内核里维护一套对象关系：服务端拥有 node，客户端持有 ref，真正跨进程的是 handle 和数据 buffer。

PR01 / ROOT

邮局

binder_proc

每个打开 /dev/binder 的进程一份。所有线程、节点、引用和待处理工作都挂在它下面。

TH02 / COUNTER

柜台

binder_thread

真正执行 BINDER_WRITE_READ 的线程。同步调用的“栈”按线程保存，而不是按进程保存。

ND03 / RECEIVER

收件人

binder_node

服务端 Binder 对象在内核里的代表。ptr + cookie 对上用户态对象，node 归属于创建它的进程。

RF04 / HANDLE

取件码

binder_ref

客户端进程内的 handle → node 映射。同一个 node 在 A、C 两个进程里可以是不同的 desc。

TX05 / PARCEL

包裹单

binder_transaction

一次调用或回复的元数据：谁发的、发给谁、用了哪个 buffer、在不在同步调用栈上。

BF06 / LOCKER

寄存柜

binder_buffer

真正装 data + offsets 的内存。它属于目标进程的 binder_alloc，不在发送方。

01 Global Map

六个对象，三条关系线

设备提供全局上下文，进程维护自己的索引；引用把客户端和服务端连起来；事务和缓冲区负责一次调用的实际传输。

包含 / 索引 指针 / 查找 跨进程引用 工作队列

读图提示：先沿实线找“谁拥有谁”，再沿虚线找“谁指向谁”。跨进程的粉色线只发生在 ref ↔ node 之间。
Process line

进程线：设备 → 上下文 → 进程 → 线程

binder_device 内嵌一份 binder_context；每个进程打开设备得到自己的 binder_proc，线程则按 tid 挂在 proc 下。

Object line

对象线：ref → node ← node->refs

客户端进程持有 binder_ref，服务端进程拥有 binder_node。node 的 refs 链表反向登记所有引用它的 ref。

Transfer line

传输线：thread → txn → buffer → node

一次调用创建 binder_transaction；数据被写入目标进程的 binder_buffer；work 项进入目标线程或进程的 todo 队列。

i
为什么有三个“容器”？ binder_proc 是生命周期与锁的边界；binder_thread 是同步调用栈的边界；binder_node 是对象身份的边界。三者职责不同，不能互相替代。
02 Process Index

binder_proc：一个进程的四棵树、两条队列、一个分配器

驱动几乎不在热路径上遍历链表找对象。binder_proc 里预置了按不同键组织的红黑树：线程按 tid、节点按用户态指针、引用按 handle 和 node 各一棵。

03 Object & Reference

node 与 ref：对象身份和进程内句柄

这是 Android Binder 最容易混淆的一对关系。binder_node 是服务端 Binder 对象在内核里的实体账本；binder_ref 是客户端进程里的一个 handle。前者回答“它是谁”，后者回答“这个进程怎么找到它”。

归属 / 索引 指针 跨进程登记
Same node · different handles
同一个 node，两个进程：A 拿到的 handle 是 1，C 拿到的是 7。数字只在本进程的 refs_by_desc 里解释。
Node identity

node 只有一个 owner

node 的 proc 指向拥有它的服务端进程，并使用用户态的 ptr + cookie 作为身份。owner 退出后 proc = NULL，node 进入 dead nodes，等待引用清理。

Handle namespace

ref 属于客户端进程

data.desc 是 handle，只在所属 binder_proc 内唯一。每条 ref 同时挂进两棵红黑树和一条 node->refs 哈希链。

Bidirectional

双向登记，各自服务不同问题

proc->refs_by_desc 让驱动从 handle 快速找到 ref；node->refs 让 node owner 死亡时能反向找到所有客户端并投递死亡通知。

BINDER_TYPE_BINDER ──▶ binder_node（内核） ──▶ BINDER_TYPE_HANDLE 发送方视角 接收方视角
i
Android 里 handle 0 是特殊值。 它不经过普通 ref 查找，而是直接指向 binder_context.binder_context_mgr_node，也就是 ServiceManager 所在的上下文管理器。普通服务的 handle 从 1 开始分配。
04 Transaction Journey

一次同步调用，8 步穿过内核

下面以 Android 常见的同步 Binder 调用为例：A 进程通过 handle 调用 B 进程中的服务。点击“下一步”或自动播放，观察 ref → node → buffer → work → transaction_stack 如何依次登场。

01 / 08 SYNC CALL

请求进入内核

客户端线程发起 BC_TRANSACTION，带上 handle、code 和用户态 data / offsets 指针。驱动开始在 A 的进程上下文里解析目标。

当前步骤 回复路径
TIME ↓ · REQUEST → REPLY

同步调用 TF_ONE_WAY = 0

  • t->from 指向发送线程，必须有回复。
  • 请求优先进入目标 thread->todo，没有可用线程时进入 proc->todo。
  • 发送线程把 t 压入 transaction_stack，阻塞等待回复。
  • 回复是另一笔 binder_transaction，目标是原发送线程。
  • 发送方的 BR_TRANSACTION_COMPLETE 会被延迟到事务完成 / 出错后。

单向调用 TF_ONE_WAY = 1

  • t->from = NULL，没有回复事务。
  • 通常进入目标 proc->todo；同一 node 已有异步事务时进入 node->async_todo。
  • 发送方立即收到 BR_TRANSACTION_COMPLETE。
  • buffer 标记为 async_transaction，消耗 free_async_space。
  • 目标进程仍需在处理完后 BC_FREE_BUFFER。
展开：transaction_stack、from_parent 与 to_parent 到底怎么串？

同步调用允许嵌套：A 调用 B，B 在处理时又调用 C。每个线程各自维护一条“正在处理的同步事务栈”，但发送侧和接收侧使用不同的指针。

发送侧（A.thread）
    transaction_stack ──▶ t1(A→B)
                         from_parent ──▶ 上一层发送事务（这里为 NULL）

接收侧（B.thread）
    transaction_stack ──▶ t1(A→B)         ← binder_thread_read 投递时压入
                         to_parent   ──▶ 上一层接收事务（这里为 NULL）

B 再调用 C 时：
    B.thread.transaction_stack ──▶ t2(B→C)
                                   from_parent ──▶ t1
    C.thread.transaction_stack ──▶ t2

回复时：
    BC_REPLY 用接收线程栈顶的 t2 找到 t2->from（B 线程），
    再把 t2 从 B.thread 的栈中弹出。

记忆法：from_parent 串起“调用者曾经发过的上一层”，to_parent 串起“接收者曾经处理过的上一层”。它们共同支持嵌套调用、回复定位与优先级继承。

05 Buffer & Allocator

包裹最终落在谁的地址空间？

答案不是发送方，而是接收方。请求 buffer 在服务端进程的 binder_alloc 中分配；回复 buffer 在客户端进程的 binder_alloc 中分配。驱动负责把用户态数据拷进目标缓冲区，再把缓冲区地址映射给对方。

内嵌 / 归属 索引 / 指针 数据拷贝
Target-side allocation
关键：同一个 binder_buffer 同时挂在 alloc->buffers 链表和 free_buffers 或 allocated_buffers 红黑树中，分别服务“按地址遍历”和“按大小 / 地址查找”。
Allocation

buffer 属于目标进程

binder_alloc_new_buf(&target_proc->alloc, ...) 在目标进程 mmap 出来的 Binder 区域里做 best-fit 分配。发送方只提供用户态数据指针。

Contents

data + offsets + extra

data 是 Parcel 字节流；offsets 标记其中 flat_binder_object 的位置；extra 放安全上下文等附加信息。

Freeing

transaction 和 buffer 分开释放

事务对象可以在投递 / 回复后释放，但 buffer 要等目标进程调用 BC_FREE_BUFFER。因此 buffer->transaction 可能先变成 NULL。

请求路径 A → B

  • buffer 在 B_proc.alloc 中分配。
  • buffer->target_node = nodeB。
  • B 用户态拿到 data.ptr = buffer->user_data。
  • B 处理完后用 BC_FREE_BUFFER 释放。

回复路径 B → A

  • 回复是新的 binder_transaction，buffer 在 A_proc.alloc 中分配。
  • 回复事务的 is_reply = 1，目标线程是请求事务的 from。
  • A 读到 BR_REPLY，用 BC_FREE_BUFFER 释放。
01 binder_alloc_new_buf() → 02 拷入 data / offsets / 翻译对象 → 03 投递，allow_user_free = 1 → 04 BC_FREE_BUFFER → 05 合并回 free_buffers
!
单向事务的“半区”规则：free_async_space 在 mmap 时初始化为区域大小的一半，用来限制 oneway 事务占用的空间；当它过低时，驱动会触发 oneway spam 检测。
06 Refcounts & Lifetime

谁让 node 活着？

Binder 的引用计数分为“node 侧”和“ref 侧”两套。点击下面的开关，直观看到哪些计数会阻止 binder_node 被回收。

Interactive · node refcount

binder_node 存活判定器

假设这是服务端进程 B 中的一个 node。只要以下任意一项非零 / 非空，node 就不能释放；全部归零后，它才会从 proc->nodes 摘除并进入释放路径。

存活

简化展示：真实释放还要考虑 has_strong_ref / has_weak_ref 的“延迟通知”路径；如果 node 曾向用户态通知过引用状态，清零后会先通过内嵌的 node->work 走一次延迟处理。

计数 / 结构属于谁代表什么释放时机
ref->data.strong / weak客户端进程该进程持有的强 / 弱 handle 引用数BC_RELEASE / BC_DECREFS 等递减，归零后清理 ref
node->internal_strong_refs服务端 node跨进程 ref 持有的强引用；每个 ref 的 strong 0→1 时 +1对应 ref 的 strong 归零时递减
node->local_strong_refs / local_weak_refs服务端 nodeowner 侧的强 / 弱引用（本地用户态；事务构造也会取强引用）BC_ACQUIRE / BC_INCREFS 与对应 DONE / RELEASE 流程
node->tmp_refs服务端 node驱动内部临时引用：查找、构造事务、遍历时保证对象不消失操作完成后 binder_put_node() 立即递减
proc->tmp_ref / thread->tmp_ref进程 / 线程防止 proc / thread 在并发路径中被释放事务构造、查找、释放等操作结束时递减

创建

第一次发送 BINDER_TYPE_BINDER 时，驱动在 owner 进程里创建 node，并插入 proc->nodes。

引用

每个接收该对象的进程都创建一条 binder_ref，拿到自己的 handle；ref 通过 node_entry 挂到 node->refs。

计数

强 / 弱引用、事务临时引用共同维持 node。此时 proc->nodes 可被查，事务可以找到 target_node。

owner 死亡

node->proc = NULL，node 移入 dead nodes；遍历 node->refs 给注册过 death 的客户端投递通知。

回收

最后一个 ref 和临时引用消失后，node 才真正释放；dead node 从全局链表摘除。

死亡通知链路 ANDROID SERVICE DEATH

Android 上层注册 DeathRecipient 后，驱动里对应一条 binder_ref_death。服务端进程死亡时，客户端会收到 BR_DEAD_BINDER，从而触发 onServiceDied() 这类回调。

01 BC_REQUEST_DEATH_NOTIFICATION → 02 binder_ref_death → 03 owner 进程退出 → 04 BR_DEAD_BINDER → 05 BC_CLEAR_DEATH_NOTIFICATION

close()
  └─▶ binder_deferred_release()
       ├─▶ binder_thread_release()
       ├─▶ binder_node_release()        → death notifications
       └─▶ binder_cleanup_ref_olocked()   → 释放 ref
TRAP 01

handle 是全局 ID？

不是。handle（desc）只在所属进程的 refs_by_desc 里有意义，同一个 node 在不同进程可以有不同 desc。

真相：node 才是对象身份，handle 只是进程内取件码。
TRAP 02

node 里存着 Parcel 数据？

不存。node 是对象账本；Parcel 数据在目标进程的 binder_buffer 里，node 只提供目标对象身份。

真相：node ↔ ref 管身份，buffer 管数据。
TRAP 03

buffer 是发送方分配的？

反了。请求 buffer 在服务端 alloc，回复 buffer 在客户端 alloc。发送方的用户缓冲区只是被拷贝的源。

真相：binder_alloc_new_buf(&target_proc->alloc, ...)
TRAP 04

所有 work 都进 proc->todo？

同步事务和回复优先进 thread->todo；异步 / 死亡通知常进 proc->todo；单向串行化用 node->async_todo。

真相：三个队列承载三种投递语义。
TRAP 05

transaction 释放 = buffer 释放？

不是。t 可以在投递 / 回复后先释放，buffer 仍由目标进程持有，直到 BC_FREE_BUFFER 才归还 alloc。

真相：两者互相指向，但生命周期解耦。
TRAP 06

一次同步调用只有一个 transaction？

请求是一个 t，回复是另一个 t′（is_reply = 1），拥有独立的 buffer，目标线程是原请求的 from。

真相：一来一回，两笔 transaction。
