第 3 章 驱动

第 1 章的地图停在 BpBinder::transact 的 else 分支最后一行：IPCThreadState::self()->transact(binderHandle(), code, data, reply, flags)。本章从这一行接着读。

IPCThreadState 是每个线程自己的 Binder 连接：一个进程里，每个调用 Binder 的线程各有一份，持有 mOut / mIn 两块缓冲区。mOut 攒要写给驱动的命令，mIn 接驱动返回的命令。

下面四个函数来自 frameworks/native/libs/binder/IPCThreadState.cpp（噪声段已按上述标记节选）：transact（808 行）、writeTransactionData（1215 行）、talkWithDriver（1092 行）、waitForResponse（987 行）。先看调用入口，再按一次同步调用实际发生的顺序往下读。

transact
├─ writeTransactionData  // 第 3 节：把命令写进 mOut
└─ waitForResponse       // 第 5 节：循环里——
     └─ talkWithDriver   //    第 4 节：ioctl 把 mOut 送进驱动

阅读顺序按数据流排：先看怎么写、再看怎么送、最后看怎么等。送数据的 talkWithDriver 实际是 waitForResponse 循环里的第一步，第 5 节会回到这个循环。

为方便阅读，代码块里的 // ← 是本站添加的阅读标注；// ……（省略：…） 是节选标记，被省略的是与主线无关的噪声段（调试日志、限制检查、遗留分支）。代码语句本身保持原样。

一、BpBinder::transact

这个函数唯一要做的事：检查代理是否还活着、处理 flags 和 stability，然后把调用交给 IPCThreadState。读的时候只看最后那个 else 分支。

status_t BpBinder::transact(
    uint32_t code, const Parcel& data, Parcel* reply, uint32_t flags)
{
    // Once a binder has died, it will never come back to life.
    if (mAlive) {
        bool privateVendor = flags & FLAG_PRIVATE_VENDOR;
        // don't send userspace flags to the kernel
        flags = flags & ~static_cast<uint32_t>(FLAG_PRIVATE_VENDOR);

        // ……（省略：stability 接口稳定性检查）

        status_t status;
        if (isRpcBinder()) [[unlikely]] { // ← 另一条 RPC Binder 路径，本章不走
            // ……（省略：RPC Binder 分支，本章不走）
        } else {
            // ……（省略：内核 Binder 被裁剪时的保护）

            status = IPCThreadState::self()->transact(binderHandle(), code, data, reply, flags); // ← 交给线程自己的 Binder 连接，本章从这里接着读
        }
        // ……（省略：大事务告警日志）

        if (status == DEAD_OBJECT) mAlive = 0; // ← 对端已死，这个代理永久失效

        return status;
    }

    return DEAD_OBJECT;
}

这段代码（BpBinder.cpp 362 行）里和本章链路相关的是 else 分支：IPCThreadState::self()->transact(binderHandle(), code, data, reply, flags)。前面 isRpcBinder() 是另一条 RPC Binder 路径，本章不展开；stability 检查和 mAlive 是对象有效性保护。

谁真正把 Parcel 写进驱动？BpBinder 只做对象和路径判断；真正打包、写进驱动、等回复的是 IPCThreadState。下一节从它的 transact 开始。

二、IPCThreadState::transact

只有两条主路：把调用写进 mOut，然后要么等回复、要么不等。节选标记里的日志和限制检查与主线无关，跳过。

status_t IPCThreadState::transact(int32_t handle,
                                  uint32_t code, const Parcel& data,
                                  Parcel* reply, uint32_t flags)
{
    LOG_ALWAYS_FATAL_IF(data.isForRpc(), "Parcel constructed for RPC, but being used with binder.");

    status_t err;

    flags |= TF_ACCEPT_FDS; // ← 允许 Parcel 携带文件描述符

    // ……（省略：事务日志）

    // ……（省略：oneway 日志）
    err = writeTransactionData(BC_TRANSACTION, flags, handle, code, data, nullptr); // ← 组装成一条命令写进 mOut

    if (err != NO_ERROR) {
        if (reply) reply->setError(err);
        return (mLastError = err);
    }

    if ((flags & TF_ONE_WAY) == 0) {
        // ……（省略：进程调用限制检查）

        // ……（省略：遗留调试日志）
        if (reply) {
            err = waitForResponse(reply); // ← 同步调用：阻塞等 BR_REPLY
        } else {
            Parcel fakeReply;
            err = waitForResponse(&fakeReply);
        }
        // ……（省略：遗留调试日志）

        IF_LOG_TRANSACTIONS() {
            std::ostringstream logStream;
            logStream << "BR_REPLY thr " << (void*)pthread_self() << " / hand " << handle << ": ";
            if (reply)
                logStream << "\t" << *reply << "\n";
            else
                logStream << "(none requested)"
                          << "\n";
            std::string message = logStream.str();
            ALOGI("%s", message.c_str());
        }
    } else {
        err = waitForResponse(nullptr, nullptr); // ← oneway：只等驱动确认，不等结果
    }

    return err;
}

这段是 IPCThreadState::transact（808 行）。主线只有四步：

  • flags |= TF_ACCEPT_FDS：允许 Parcel 携带文件描述符。
  • writeTransactionData(BC_TRANSACTION, flags, handle, code, data, nullptr)：把这次调用组装成一条 BC_TRANSACTION 命令写进 mOut。
  • 同步分支 (flags & TF_ONE_WAY) == 0：waitForResponse(reply) 等回复；没有 reply 时传一个临时 fakeReply 走同一流程。
  • oneway 分支：waitForResponse(nullptr, nullptr)，只等 BR_TRANSACTION_COMPLETE，不等业务返回值。

writeTransactionData 究竟把什么写进了 mOut？下一节看这个函数。

三、writeTransactionData

只做两件事：填 binder_transaction_data，再追加到 mOut。结构体定义留到第 3 章，本章只需知道每个字段填的是什么。

status_t IPCThreadState::writeTransactionData(int32_t cmd, uint32_t binderFlags,
    int32_t handle, uint32_t code, const Parcel& data, status_t* statusBuffer)
{
    binder_transaction_data tr;

    tr.target.ptr = 0; /* Don't pass uninitialized stack data to a remote process */
    tr.target.handle = handle; // ← 目标 Binder 的数字句柄
    tr.code = code; // ← 方法编号，服务端靠它分派
    tr.flags = binderFlags;
    tr.cookie = 0;
    tr.sender_pid = 0;
    tr.sender_euid = 0;

    const status_t err = data.errorCheck();
    if (err == NO_ERROR) {
        tr.data_size = data.ipcDataSize();
        tr.data.ptr.buffer = data.ipcData(); // ← 直接指向 Parcel 内存，不复制
        tr.offsets_size = data.ipcObjectsCount()*sizeof(binder_size_t);
        tr.data.ptr.offsets = data.ipcObjects(); // ← Binder 对象的偏移表
    } else if (statusBuffer) {
        tr.flags |= TF_STATUS_CODE;
        *statusBuffer = err;
        tr.data_size = sizeof(status_t);
        tr.data.ptr.buffer = reinterpret_cast<uintptr_t>(statusBuffer);
        tr.offsets_size = 0;
        tr.data.ptr.offsets = 0;
    } else {
        return (mLastError = err);
    }

    mOut.writeInt32(cmd); // ← BC_TRANSACTION + 结构体，此时驱动还没见到
    mOut.write(&tr, sizeof(tr));

    return NO_ERROR;
}

这个函数（1215 行）只做两件事：填 binder_transaction_data，再把它追加到 mOut。结构体定义留到第 3 章，本章只看填了哪些字段：

  • tr.target.handle = handle：目标 Binder 的句柄；客户端用它指向远端对象。
  • tr.code = code：方法编号，服务端靠它分派到具体接口方法。
  • tr.flags = binderFlags：这次事务的标志，包含同步 / oneway、TF_ACCEPT_FDS 等。
  • tr.data.ptr.buffer = data.ipcData()：直接指向 Parcel 的内存，不复制；tr.data_size 是这段数据的长度。
  • tr.offsets_size / tr.data.ptr.offsets = data.ipcObjects()：Binder 对象在 Parcel 里的偏移表，驱动靠它修正对象引用。

其余字段清零，避免把栈上的未初始化数据传给远端。最后两行把命令号和结构体写进 mOut：mOut.writeInt32(cmd)（调用方传入的 BC_TRANSACTION）和 mOut.write(&tr, sizeof(tr))。此时数据还在用户空间缓冲区，驱动还没有看到它。

mOut 只是内存，真正把数据送进驱动的 talkWithDriver 不是由 writeTransactionData 调用的：transact 下一步调用的是 waitForResponse，而 talkWithDriver 是它循环里的第一步。本节先看这个 "送" 的动作。

四、talkWithDriver

talkWithDriver 的调用方是 waitForResponse（第 5 节回到它的循环），本节只看这一个函数。

把 mOut / mIn 接到一个 binder_write_read 上，发一次 ioctl。抓三个点：写什么、读什么、返回后怎么清理。

status_t IPCThreadState::talkWithDriver(bool doReceive)
{
    if (mProcess->mDriverFD < 0) {
        return -EBADF;
    }

    binder_write_read bwr;

    // Is the read buffer empty?
    const bool needRead = mIn.dataPosition() >= mIn.dataSize();

    // We don't want to write anything if we are still reading
    // from data left in the input buffer and the caller
    // has requested to read the next data.
    const size_t outAvail = (!doReceive || needRead) ? mOut.dataSize() : 0;

    bwr.write_size = outAvail;
    bwr.write_buffer = (uintptr_t)mOut.data(); // ← 写缓冲接 mOut，读缓冲接 mIn

    // This is what we'll read.
    if (doReceive && needRead) {
        bwr.read_size = mIn.dataCapacity();
        bwr.read_buffer = (uintptr_t)mIn.data();
    } else {
        bwr.read_size = 0;
        bwr.read_buffer = 0;
    }

    // ……（省略：调试日志）

    // Return immediately if there is nothing to do.
    if ((bwr.write_size == 0) && (bwr.read_size == 0)) return NO_ERROR;

    bwr.write_consumed = 0;
    bwr.read_consumed = 0;
    status_t err;
    do {
        // ……（省略：调试日志）
#if defined(__ANDROID__)
        if (ioctl(mProcess->mDriverFD, BINDER_WRITE_READ, &bwr) >= 0) // ← 一次系统调用：写 BC_*、读回 BR_*
            err = NO_ERROR;
        else
            err = -errno;
#else
        err = INVALID_OPERATION;
#endif
        if (mProcess->mDriverFD < 0) {
            err = -EBADF;
        }
        // ……（省略：调试日志）
    } while (err == -EINTR); // ← 被信号打断就重试

    // ……（省略：调试日志）

    if (err >= NO_ERROR) {
        if (bwr.write_consumed > 0) {
            if (bwr.write_consumed < mOut.dataSize())
                LOG_ALWAYS_FATAL("Driver did not consume write buffer. "
                                 "err: %s consumed: %zu of %zu",
                                 statusToString(err).c_str(),
                                 (size_t)bwr.write_consumed,
                                 mOut.dataSize());
            else {
                mOut.setDataSize(0);
                processPostWriteDerefs();
            }
        }
        if (bwr.read_consumed > 0) {
            mIn.setDataSize(bwr.read_consumed); // ← 驱动读回多少，mIn 就有多少
            mIn.setDataPosition(0);
        }
        // ……（省略：调试日志）
        return NO_ERROR;
    }

    ALOGE_IF(mProcess->mDriverFD >= 0,
             "Driver returned error (%s). This is a bug in either libbinder or the driver. This "
             "thread's connection to %s will no longer work.",
             statusToString(err).c_str(), mProcess->mDriverName.c_str());
    return err;
}

这个函数（1092 行）把两块缓冲区接到一个 binder_write_read 上，然后发一次 ioctl。读的时候抓住四点：

  • needRead 判断 mIn 是否已经读完；write_size / write_buffer 指向 mOut，read_size / read_buffer 指向 mIn 的空闲空间。
  • ioctl(mProcess->mDriverFD, BINDER_WRITE_READ, &bwr)：一次系统调用同时把 BC_* 命令写给驱动、把驱动产生的 BR_* 命令读回来。
  • do { ... } while (err == -EINTR)：被信号打断就重试，其他错误直接返回。
  • 成功返回后，bwr.write_consumed 清空 mOut，bwr.read_consumed 设置 mIn 的大小并把读位置归零。

ioctl 返回后 mIn 里是驱动发回的 BR_* 命令，谁解析它们？下一节 waitForResponse。

五、waitForResponse

同步调用的等待循环：talkWithDriver 取回命令，读一个 cmd，按类型处理。主线只有 BR_REPLY；default 分支是嵌套调用，第 4 章再读。

status_t IPCThreadState::waitForResponse(Parcel *reply, status_t *acquireResult)
{
    uint32_t cmd;
    int32_t err;

    while (1) {
        if ((err=talkWithDriver()) < NO_ERROR) break; // ← 去驱动拿命令
        err = mIn.errorCheck();
        if (err < NO_ERROR) break;
        if (mIn.dataAvail() == 0) continue;

        cmd = (uint32_t)mIn.readInt32(); // ← mIn 开头是命令号

        // ……（省略：调试日志）

        switch (cmd) {
        // ……（省略：oneway 刷屏告警 case）
        case BR_TRANSACTION_COMPLETE: // ← oneway 的完成标志
            if (!reply && !acquireResult) goto finish;
            break;

        // ……（省略：冻结进程相关 case）

        case BR_DEAD_REPLY:
            err = DEAD_OBJECT;
            goto finish;

        case BR_FAILED_REPLY:
            err = FAILED_TRANSACTION;
            goto finish;

        // ……（省略：冻结进程相关 case）

        // ……（省略：引用计数结果 case）

        case BR_REPLY: // ← 主线：服务端把结果送回来了
            {
                binder_transaction_data tr;
                err = mIn.read(&tr, sizeof(tr));
                ALOG_ASSERT(err == NO_ERROR, "Not enough command data for brREPLY");
                if (err != NO_ERROR) goto finish;

                if (reply) {
                    if ((tr.flags & TF_STATUS_CODE) == 0) {
                        reply->ipcSetDataReference( // ← 驱动缓冲区直接挂给 Parcel，零拷贝
                            reinterpret_cast<const uint8_t*>(tr.data.ptr.buffer),
                            tr.data_size,
                            reinterpret_cast<const binder_size_t*>(tr.data.ptr.offsets),
                            tr.offsets_size/sizeof(binder_size_t),
                            freeBuffer);
                    } else {
                        err = *reinterpret_cast<const status_t*>(tr.data.ptr.buffer);
                        freeBuffer(reinterpret_cast<const uint8_t*>(tr.data.ptr.buffer),
                                   tr.data_size,
                                   reinterpret_cast<const binder_size_t*>(tr.data.ptr.offsets),
                                   tr.offsets_size / sizeof(binder_size_t));
                    }
                } else {
                    freeBuffer(reinterpret_cast<const uint8_t*>(tr.data.ptr.buffer), tr.data_size,
                               reinterpret_cast<const binder_size_t*>(tr.data.ptr.offsets),
                               tr.offsets_size / sizeof(binder_size_t));
                    continue;
                }
            }
            goto finish;

        default:
            err = executeCommand(cmd); // ← 嵌套调用，第 4 章
            if (err != NO_ERROR) goto finish;
            break;
        }
    }

finish:
    if (err != NO_ERROR) {
        if (acquireResult) *acquireResult = err;
        if (reply) reply->setError(err);
        mLastError = err;
        logExtendedError();
    }

    return err;
}

这个函数（987 行）是同步调用的等待循环：talkWithDriver 取回命令，读一个 cmd，按命令类型处理。主线如下：

  • while (1)：talkWithDriver 返回错误就跳出；mIn.dataAvail() == 0 时继续下一轮。
  • BR_REPLY：读出 binder_transaction_data，把回复数据接上 reply Parcel（见下）；带 TF_STATUS_CODE 时从 buffer 读错误码并释放缓冲区。
  • BR_TRANSACTION_COMPLETE：oneway 完成的标志；没有 reply 和 acquireResult 时直接结束。同步调用收到它只表示写端已入队，还要继续等 BR_REPLY。
  • BR_DEAD_REPLY 转成 DEAD_OBJECT，BR_FAILED_REPLY 转成 FAILED_TRANSACTION；其他错误分支同样走 finish 返回。
  • default: executeCommand(cmd)：调用方线程也可能收到 BR_TRANSACTION，那是嵌套进来的新调用，留到第 4 章。

BR_REPLY 里这段地址为什么能直接用：每个 Binder 进程启动时 ProcessState 会 mmap 一块约 1MB 的区域交给驱动管理（本树 ProcessState.cpp 574 行）。服务端写回的回复数据，驱动就放进你自己进程的 这块 mmap 区域，再把地址通过 BR_REPLY 告诉你——所以 ipcSetDataReference 只需把 Parcel 的数据指针直接指过去，不 malloc、不 memcpy。这块内存属于驱动，Parcel 只是借用，因此登记 freeBuffer 回调：Parcel 析构或被复用时会向驱动发 BC_FREE_BUFFER 归还缓冲区，不还的话进程那 1MB 会被事务缓冲区耗尽。 mmap 区域怎么分配缓冲区，第 3 章读驱动时再看。

BR_REPLY 里这段内存是驱动从服务端缓冲区送回来的：驱动怎么找到目标、怎么把数据送回来？第 3 章从 binder_ioctl 开始读。
